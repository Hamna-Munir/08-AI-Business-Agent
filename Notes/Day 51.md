# Day 51 — Business Data + Structured Analysis

**Objective:** Teach the agent to understand business data and analyze it in a structured form, using real KPIs instead of vague summaries.

---

## 📖 Theory

### Structured business data

Business data lives in tables: each row is one thing (a customer, a product, an order, a sale) and each column is one fact about it. An agent can only reason reliably over data that has a predictable shape, because a tool can only filter, group, and sum what it knows the names of.

### CSV / JSON

CSV is the simplest way to move tabular business data around (exports from Excel, a POS system, a CRM). JSON is what tools hand back to the agent: a list of dicts with named fields. In this project the flow is CSV → SQLite → tool functions → JSON-serializable dicts → analyzer → LLM.

### Data schemas

A schema is the agreement about what each table contains. This project's four tables:

```
customers(customer_id, name, region, segment, signup_date)
products(product_id, name, category, base_price)
orders(order_id, customer_id, order_date, region)
sales(sale_id, order_id, product_id, quantity, unit_price, revenue)
```

`orders` is the header (who bought, when, where) and `sales` holds the line items (what, how many, at what price). Keeping them separate is what makes it possible to count **orders** and **units** and **revenue** independently, which Day 56's analysis depends on.

### Pydantic (and where it fits here)

In Week 7, Pydantic validated the `MeetingRequest` the LLM extracted from messy text. In this project the structure comes from the SQLite schema instead, because the data is already tabular and trusted, not LLM-extracted. Pydantic would be the right tool again if the agent had to parse *uploaded* business files of unknown shape (a good future extension).

### Business metrics and KPIs

A KPI is a number that answers a business question. The ones used in this project:

| KPI | Meaning | Where it comes from |
|---|---|---|
| Revenue | Money earned | `SUM(sales.revenue)` |
| Orders | Number of purchases | `COUNT(DISTINCT orders.order_id)` |
| Units | Items sold | `SUM(sales.quantity)` |
| Average order value | Revenue per order | revenue ÷ orders |
| Average unit price | Price actually paid per item | `AVG(sales.unit_price)` |
| Customers by region/segment | Who is buying | `customers` table |

Profit and conversion rate need cost and visitor data that this dataset does not have. The agent should say so if asked, not guess them.

### Why revenue alone is not enough

Revenue = units × price. If revenue falls, either fewer units sold (demand problem) or each unit sold for less (price problem). Those need opposite fixes, so the data must expose orders, units, and price separately.

### Why the dataset has a story in it

Random data has no answer to find. So the generator in `database.py` deliberately gives one product, **UrbanTote Backpack**, a price cut in June while its order count stays flat. This gives Day 56's "why did revenue drop?" a real, checkable answer.

## 🐞 Common Errors

| Error | Likely Cause | Fix |
|---|---|---|
| Revenue totals look doubled | Joining `orders` to `sales` and summing an order-level column | Sum only line-item columns (`sales.revenue`) and use `COUNT(DISTINCT order_id)` for orders |
| "No such table" error | Database not built yet | Run `python -m src.database` (the app also calls `build_database()` on startup) |
| Month filter returns nothing | Date format mismatch | Dates are stored as ISO text; filter with `strftime('%Y-%m', order_date) = '2026-06'` |
| Data looks different every run | Random generation without a seed | The generator uses `random.Random(7)`, keep it fixed |
| Agent confidently answers a profit question | No cost data exists | Return insufficient evidence instead of inventing a margin |
